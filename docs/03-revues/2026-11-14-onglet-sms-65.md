# Onglet SMS de la console (carte #65, I-2) — compte rendu et limites déclarées

Date : 2026-11-14. Couloir A. Branche `t4-65-onglet-sms`. Décisions du superviseur technique du
2026-10-26 (D1 à D4) et du 2026-11-14 (I-2).

## Ce que fait l'onglet

`/sms` affiche, pour un numéro de la plage fictive 677000000–677009999 (ED-09), le **dernier** SMS
simulé reçu par la SIM **actuellement** rattachée à ce numéro : numéro, IMSI qui l'a reçu, heure du
dernier changement HLR, code, heure de remise. Le numéro est résolu en IMSI par `GET /hlr` du cœur ;
le code et son heure de remise sont lus sur isc-sim (`GET /inbox?imsi=`, champ `deliveredAt` ajouté).
La console ne lit aucune base et n'écrit rien. Le code est affiché en clair (D1) : c'est le but de
l'onglet, la propriétaire le lit et le dicte au testeur.

## Limites déclarées

| # | Limite | Pourquoi elle est acceptée / conduite à tenir |
|---|---|---|
| L-65-1 | **Redémarrer isc-sim vide les boîtes SMS** (et la chronologie d'attaque) : elles sont en mémoire, volatiles par construction. | Un canal, pas un journal. **Ne jamais redémarrer isc-sim pendant une démonstration ni pendant un test.** Si c'est arrivé, l'onglet affiche « Aucun SMS reçu par cette SIM » : redemander un nouveau code depuis l'application. |
| L-65-2 | Seul le **dernier** code par SIM est gardé : un nouvel envoi remplace le précédent, code et heure. | D4. L'heure de remise permet de vérifier que le code affiché est bien celui qui vient d'être demandé. |
| L-65-3 | Le **nom du titulaire** n'est pas affiché. | Il n'existe dans aucune table (dette ED-11, #18). |
| L-65-4 | Le code est lisible par quiconque ouvre la console. | La console n'écoute qu'en boucle locale dans la VM (#66) ; elle ne doit jamais être publiée sur le tailnet. Attention, en développement sur le poste, `next dev` écoute par défaut sur **toutes** les interfaces : le lancer avec `-H 127.0.0.1`. |
| L-65-5 | **La construction de la console a besoin d'Internet** (voir ci-dessous). | Proposition de police locale à décider ; d'ici là, construire la console quand le réseau de la VM le permet, jamais le jour d'une démonstration. |

## La construction de la console dépend d'Internet (prouvé le 2026-11-14)

Essai dans la VM sur une copie de `console/` dans `/tmp`, images de test seulement, pile servie non
touchée :

1. `docker build --network=none` du Dockerfile de la console : échec dès `npm ci`, qui n'était pas
   en cache et a besoin du registre npm.
2. Dépendances installées avec le réseau dans une image intermédiaire, puis `npm run build` **sans
   réseau** au-dessus : échec sur les deux polices.

```text
#8 44.08 Error: next/font: error:
#8 44.08 Failed to fetch IBM Plex Mono from Google Fonts.
#8 44.08 If you are offline or behind a proxy, self-host the font with next/font/local, or set HTTP_PROXY/HTTPS_PROXY so Next.js can reach fonts.googleapis.com.
#8 44.08 Error: next/font: error:
#8 44.08 Failed to fetch Sora from Google Fonts.
```

`console/app/layout.tsx` charge Sora et IBM Plex Mono par `next/font/google` : Next.js (16.3.3)
télécharge les fichiers depuis `fonts.googleapis.com` et `fonts.gstatic.com` **à chaque
construction**. L'image de la console servie date du 2026-10-24 ; elle n'a pas été reconstruite
depuis.

**Proposition (non appliquée, décision de la propriétaire) :** passer à `next/font/local`, qui fait
partie de Next.js (aucune bibliothèque nouvelle), avec les fichiers `.woff2` de Sora et d'IBM Plex
Mono (licence SIL Open Font License) versionnés dans `console/app/fonts/`. La construction ne
dépendrait plus de Google ; `npm ci` resterait dépendant du registre npm tant que `package-lock.json`
change, la couche Docker étant en cache sinon.

## Vérification à l'écran (2026-11-14) et ce qui ne l'est pas

Sur le poste : console en `next dev -H 127.0.0.1` (la construction complète est impossible sous
Windows, défaut amont vercel/next.js#87719), isc-sim de la branche, et un **faux cœur** qui ne sert
que `/mode` et `/hlr` (677000001 avec heure de changement, 677000002 sans). Un SMS de test a été remis
à 677000001 avec un code tiré au hasard, jamais affiché. Edge sans interface, piloté par le protocole
DevTools ; avant chaque capture, la case du code est couverte d'un bloc opaque, et seule la forme du
code (six chiffres) est vérifiée.

| Cas | Français | Anglais |
|---|---|---|
| 699000001 (hors plage) | bouton désactivé, « Saisissez 9 chiffres dans la plage fictive 677000000–677009999. » ; l'API rend 400 `INVALID_MSISDN` | bouton désactivé, message anglais |
| 677009999 (dans la plage, inconnu du HLR) | « Ce numéro n'existe pas dans le HLR simulé : vérifiez le numéro du compte de démonstration. » ; 404 `UNKNOWN_MSISDN` | message anglais |
| 677000001 (SMS remis) | IMSI 624010000000000, changement HLR « 14/11/2026 16:35:00 UTC+1 », code de six chiffres (masqué sur la capture), remis à « 14/11/2026 18:57:19 UTC+1 » | mêmes valeurs, « GMT+1 » |
| 677000002 (aucun SMS) | « Aucun SMS reçu par cette SIM. », changement HLR « non fournie » | « not provided » |

**Non vérifié :** l'onglet contre la pile réelle (vrai cœur, vrai OTP de l'application) — ce sera la
fenêtre 7 ; l'affichage sur un écran réel et à 200 % de taille de police.
