# ADR-039 — Connexions persistantes de l'application : réserve plus courte que le serveur, rejeu des lectures seulement

**Statut :** ACCEPTÉ — valeurs acceptées par le propriétaire (consignes consolidées de la carte B1a) ; rédigé par la session Mobile (défaut D9), accepté sur le fond par le tech lead
**Date :** 2026-10-11
**Source :** passe sur appareil réel du 2026-10-08 (défaut D9, reproduit 4 fois) ; ISC-MOB-SPEC v1.2 §7.4 (jamais de renvoi automatique d'une opération) ; ADR-037 (pile mobile, amendement M-07 : `retryOnConnectionFailure(false)`) ; ADR-018 (charge signée, nonce à usage unique)

## Contexte

L'application garde les connexions HTTP en réserve (pool d'OkHttp, 5 minutes par défaut). Le serveur, lui, ferme une connexion inactive après son propre délai. Entre les deux, la connexion est morte côté serveur et encore « en réserve » côté téléphone (`CLOSE_WAIT`). OkHttp ne vérifie l'état d'une connexion en réserve que si elle est inactive depuis plus de dix secondes **et** que la requête n'est pas un GET ; sinon il la réutilise telle quelle. La requête suivante échoue alors (« unexpected end of stream ») et, comme l'application ne rejoue jamais rien (amendement M-07), l'usager lit « Connexion impossible » alors que le serveur est joignable. Observé sur la tablette après le défi de session, puis sur les lectures de l'accueil ; disparaît quand plus de 5 minutes séparent deux requêtes (éviction du pool).

Le renvoi automatique de toute requête n'est pas acceptable : un envoi d'argent ou une réponse d'alerte reçus par le serveur mais dont la réponse s'est perdue ne doivent jamais être rejoués (SPEC §7.4 ; le nonce est consommé).

## Décision

1. **La réserve de l'application est plus courte que celle du serveur.** Deux paramètres nommés dans `config/ruleset.yaml` : `APP_CONN_KEEPALIVE` (durée pendant laquelle l'application garde une connexion inactive en réserve) et `SERVER_CONN_KEEPALIVE` (durée après laquelle le serveur ferme une connexion inactive). La construction de l'application **échoue** si `APP_CONN_KEEPALIVE` n'est pas strictement inférieur à `SERVER_CONN_KEEPALIVE`. Valeurs **acceptées par le propriétaire** : `APP_CONN_KEEPALIVE` = PT20S et `SERVER_CONN_KEEPALIVE` = PT30S. Le faux serveur applique `SERVER_CONN_KEEPALIVE` (HTTP/1.1, connexions persistantes) ; le cœur devra l'appliquer à ses routes mobiles (`keepAliveTimeout` de Tomcat) quand il les exposera.
2. **Rejeu automatique des lectures seulement, une fois, sur une connexion neuve** (arbitrage B1a-5 : le ticket `POST /nonce` est une exception écrite à « aucun POST n'est rejoué »). Une liste fermée de requêtes sans effet sur l'argent ni sur l'état du compte peut être rejouée après une panne de connexion : tous les `GET` (défi de session, compte, opérations, titulaire, alertes) et `POST /nonce` (le ticket : un nonce émis puis jamais utilisé est sans effet). **Aucune autre requête n'est rejouée** : ouverture de session, enrôlement, envoi, annulation, réponse à une alerte, rotation, déliaison. La liste est dans le code (`ReadRetryInterceptor`) et prouvée par des tests qui reproduisent la connexion coupée.

## Alternatives rejetées

- **`retryOnConnectionFailure(true)` d'OkHttp.** Rejoue aussi les POST d'argent sur une connexion réutilisée : refusé par l'amendement M-07 d'ADR-037, maintenu.
- **Fermer chaque connexion après usage (`Connection: close`).** Supprime le pool, donc le défaut, mais impose une poignée de main TLS par requête sur un réseau mobile lent ; la réserve bornée garde l'avantage des connexions persistantes.
- **Ne rien rejouer et réduire seulement la réserve.** Laisse une fenêtre (changement de réseau, serveur redémarré) où une simple lecture échoue sans raison visible pour l'usager.

## Conséquences

- `config/ruleset.yaml` : `APP_CONN_KEEPALIVE` et `SERVER_CONN_KEEPALIVE` ; aucune valeur en dur (porte `named-params`).
- `mobile/` : `ConnectionPool` construit avec `APP_CONN_KEEPALIVE` ; `ReadRetryInterceptor` ; tests `DailyRepositoryTest` : une lecture après une connexion fermée par le serveur réussit sur une connexion neuve ; un envoi dans la même situation échoue sans jamais être renvoyé (le serveur ne reçoit qu'une requête).
- `tools/mobile-mock/` : HTTP/1.1 persistant, fermeture après `SERVER_CONN_KEEPALIVE` d'inactivité.
- **La carte B3 applique `SERVER_CONN_KEEPALIVE` aux routes `/mobile/v1` du cœur.** Tant que ce n'est pas fait, le cœur garde la valeur par défaut de son serveur web.
