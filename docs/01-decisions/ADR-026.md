# ADR-026 — La construction et la validation de la console appartiennent à la VM ; le poste Windows ne fait que la compilation légère

**Statut :** FERME
**Date :** 2026-09-13
**Source :** ISC-DEPLOY §5.2 (VM pour toute mesure publiable) ; quatre incidents du couple Docker/Next.js sur le poste Windows ; décision du propriétaire du 13/09/2026
**Remplace :** ADR-026 v1 (PROVISOIRE, 2026-08-26), qui présentait le mode compile seul comme un contournement temporaire *en attendant* le correctif amont. La position ci-dessous n'attend plus rien : elle est définitive.

## Contexte

Quatre difficultés distinctes du même couple **Docker + Next.js sur le poste Windows** se sont accumulées :

1. **Prerender `next build` cassé sur Windows** — `InvariantError: Expected workStore to be initialized`, bug amont ouvert (vercel/next.js#87719), reproduit avec Next 15.5 et 16.3, webpack et Turbopack, y compris sur un `create-next-app` vierge. Seule la phase de prerender casse ; la compilation passe.
2. **EPERM/`rmdir` transitoire sur `console/.next`** — un verrou de fichier (antivirus / indexation) empêche par intermittence la suppression de `.next`, faisant échouer le build tant que le dossier n'est pas nettoyé à la main.
3. **Plantage mémoire de Docker Desktop** pendant le `next build` du conteneur console lors d'un essai antérieur.
4. **Corruption du stockage containerd** (13/09/2026) : `read-only file system` puis `input/output error` sur les snapshots overlayfs, aboutissant à un `exec format error` sur **toute** image Linux (même `alpine echo`) — non récupérable par deux redémarrages propres, ne se réparant que par un « Clean/Purge data » destructif.

Réparer au cas par cas ne dit rien sur la fois suivante. Une cinquième occurrence le jour de la soutenance ferait tomber la démonstration. La VM `isc-vm` est saine, Linux natif, avec Internet depuis le 30/08/2026 ; le même `next build` complet y passe proprement (mesuré le 13/09 : `next build` ≈ 86 s, image console complète ≈ 8 min, `verify_console.sh` VERT, latence flux ≈ 310 ms).

## Décision

La **construction** et la **validation** de la console (image Docker, `next build` complet, `verify_console.sh`, toute mesure de délai) **appartiennent à la VM `isc-vm`** (et à la CI Linux). Le **poste Windows ne fait que la compilation légère** — `next build --experimental-build-mode compile`, sans prerender — pour le retour rapide de `make check`. Cette répartition est **définitive**, non plus conditionnée au correctif amont : même si vercel/next.js#87719 est corrigé, la validation publiable de la console reste sur la VM par ISC-DEPLOY §5.2.

Conduite en cas de nouvelle panne Docker sur le poste : **on ne répare pas, on bascule** sur la VM (voir l'incident consigné le 2026-09-13 dans `docs/03-revues/`).

## Alternatives rejetées

- **Réparer Docker Desktop sur le poste** (Clean/Purge data, réinstallation WSL2) : action destructive qui ne garantit rien pour la suite ; quatre occurrences montrent un couple instable, pas un incident isolé.
- **Builder la console dans Docker à chaque `make check` local** : ~8 min par exécution sur ce poste quand Docker fonctionne, et impossible quand il est cassé.
- **Revenir à Next.js 14** : version dépassée pour un projet soutenu en 2027 ; n'adresse ni la mémoire ni la corruption Docker.

## Conséquences

- Parité poste/VM (ISC-DEPLOY §6.2) : le poste vérifie la compilation, la VM vérifie le build complet et le comportement runtime. Écart assumé et **fermé**, non plus provisoire.
- `make check` sous Windows reste rapide (compile seul) ; la porte lourde et `verify_console.sh` tournent sur la VM.
- Toute mesure de délai publiable (critère #10, latence flux) est prise sur la VM, jamais sur Windows — ce que `verify_console.sh` n'aurait jamais dû faire sur le poste.

## Mise à jour du 15/09/2026 — Docker Desktop désinstallé du poste : la répartition devient une contrainte absolue

Le disque `C:` du poste s'est retrouvé **plein (0 Go / 471)**, suspendant la VM à répétition (son `.vdi` dynamique ne pouvait plus grossir) — cause d'abord diagnostiquée à tort comme un manque de mémoire. Sous **levée explicite du propriétaire** (trace : `docs/03-revues/2026-09-15-levee-merge-push-t2-12-main.md` pour le contexte de session, motif détaillé dans `docs/03-revues/2026-09-15-maj-adr-026-desinstallation-docker-desktop.md`), Docker Desktop — corrompu depuis le 13/09 (`exec format error`, décrit ci-dessus) et inutilisé depuis — a été **désinstallé** pour libérer l'espace : distribution WSL `docker-desktop` désenregistrée, puis son `.vhdx` orphelin (9,5 Go) supprimé.

**Conséquence sur la décision.** Le poste **n'a plus aucun Docker**. La formulation « le poste ne fait que la compilation légère » n'est donc plus une *répartition* d'un Docker présent-mais-peu-sollicité : c'est une **contrainte absolue**.

- **Tout** travail Docker — build d'images, pile `make up`, `check-stack`, `verify_*.sh`, toute mesure publiable — se fait **exclusivement** dans la VM `isc-vm` (et la CI Linux). Il n'y a plus rien à « basculer » ni à « réparer » sur le poste : la VM est le **seul** environnement Docker.
- Le poste fait la **compilation légère** (`next build ... compile`) et les **portes légères** (`make check` : build/format/unit/arch/contract/check-docs/secrets/fictitious-msisdn/named-params), **sans Docker**.
- **Preuve.** Le 15/09, après désinstallation, `make check` passe **VERT sur `main`** avec Docker **absent** du poste — confirmant que le rôle du poste ne dépend d'aucun Docker.

L'alternative « Réparer Docker Desktop sur le poste » (déjà rejetée ci-dessus) est désormais **sans objet** : il n'y a plus d'installation à réparer. Une réinstallation future serait une décision distincte, non requise par ce projet.

Suivi éventuel (hors de ma main, CLAUDE.md §2) : si `ISC-DEPLOY §6.2` décrit un Docker local sur le poste, sa mise en cohérence relève d'une nouvelle version du document par l'encadrement.
