# ADR-041 — Activation de la clé d'appareil liée à la confirmation du code de récupération

**Statut :** VERROUILLÉ (2026-10-16). Autorité déléguée au tech lead par la propriétaire.
**Source :** décisions propriétaire des 2026-09-25 et 2026-10-10 (code de
récupération unique, montré une fois, hachage stocké ; écran E-09 avec retape
complète) ; invariant D4 ; ADR-018 (format signé) ; ED-01 (séparation des schémas).
**Remplace :** la version v1 de cet ADR, dont deux défauts ont été relevés par la
session mobile avant toute implémentation (voir « Historique » en fin de document).

## Contexte

La preuve d'identité du système n'est plus le numéro ni la SIM, mais l'appareil
enrôlé (clé EC P-256 non exportable, Android Keystore) et le PIN applicatif.

Conséquence directe : si l'utilisateur perd son appareil, il perd sa preuve
d'identité. Son unique voie de retour est le **code de récupération**. Le contact
de confiance et l'e-mail de récupération ont été ABANDONNÉS ; la procédure
« code perdu » (agence + pièce d'identité) est une LIMITE DÉCLARÉE, lourde.

Le code de récupération n'est donc pas un confort : c'est la seule porte de secours.

**Le risque traité.** Si la clé devenait ACTIVE dès la fin de l'enrôlement, l'application
fonctionnerait immédiatement. L'écran du code s'afficherait alors que l'utilisateur est
déjà « entré ». Il peut fermer l'application, être interrompu, remettre à plus tard. Il
obtient un compte pleinement fonctionnel SANS aucun code noté — une bombe à retardement
qui explose le jour où il casse son téléphone.

## Décision

**1. La clé d'appareil a trois états : EN ATTENTE (PENDING) → ACTIVE → RÉVOQUÉE.**
(Remplace les deux états ACTIVE / RÉVOQUÉE du tech lead.)

**2. À `/enrolment/complete`, la clé est enregistrée en EN ATTENTE.** Le compte
n'est pas utilisable.

**3. La clé ne devient ACTIVE qu'à `/recovery-code/confirm`**, après que
l'utilisateur a retapé le code EN ENTIER sur l'écran E-09 (masqué sauf les deux
derniers caractères, aucun copier-coller).

**Invariant D4 : la copie du code ne peut pas être sautée.** Ce n'est plus une
question de discipline de l'utilisateur, c'est mécanique. Pas de code confirmé,
pas de compte.

**4. Deux routes côté PDP :**
- `POST /device/register` → `200 {deviceId, recoveryCode}` | `422`
  Enregistre la clé en EN ATTENTE après vérification de l'attestation et du défi signé.
- `POST /device/activate` → `200` | `401`
  Vérifie le code de récupération et fait passer la clé à ACTIVE.

**5. Le code de récupération est produit CÔTÉ PDP.** Seul un hachage salé est
conservé (`pdp.recovery_code`). Le code en clair est renvoyé UNE SEULE FOIS, à
l'enregistrement, et n'est jamais réaffichable — ni par l'application, ni par
l'opérateur, ni par le serveur.
Format : 6 caractères, alphabet sans 0/O/1/I/L, présenté XXX-XXX, remplacé à
chaque réenrôlement.

**6. Répartition des schémas (ED-01, aucune table partagée, aucune clé étrangère
inter-schéma) :**
- schéma `core` : enrôlement, PIN, sessions ;
- schéma `pdp` : clé d'appareil, nonce, code de récupération.

## Conséquences

- Un utilisateur qui ferme l'application avant E-09 doit recommencer l'enrôlement.
  C'est voulu : le coût est une minute, contre un compte définitivement perdu.
- Aucun compte ne peut exister sans code de récupération confirmé.
- Le PDP devient l'autorité sur le cycle de vie de la clé ; le cœur ne le connaît
  qu'à travers les deux routes ci-dessus.
- `/recovery-code/confirm` (cœur) appelle `/device/activate` (PDP). Un échec côté
  PDP laisse la clé EN ATTENTE : l'état ne progresse jamais sur une erreur.

## Alternatives écartées

- **Clé ACTIVE dès `/enrolment/complete`, écran du code ensuite** (version v1 de cet
  ADR) : écartée, elle rend D4 contournable. Défaut relevé par la session mobile.
- **Aucune route de vérification du code côté PDP** (version v1) : écartée, le cœur
  ne peut pas vérifier un hachage qu'il ne détient pas (ED-01).
- **Code produit côté cœur** : écartée, le code protège la clé, qui vit dans le PDP.
  Les deux doivent partager la même frontière de confiance.
- **Deuxième chance « plus tard »** : écartée, elle réintroduit exactement le
  contournement que D4 interdit.

## Limites déclarées

- L'utilisateur qui perd à la fois son appareil ET son code doit passer par
  l'agence avec une pièce d'identité (décision propriétaire du 2026-10-10).
- Le code est noté sur papier : sa protection physique échappe au système.
- Essais du code : 2, puis délais croissants sur l'appareil. Le compte n'est
  JAMAIS bloqué (décision du 2026-09-25, inchangée).

## Historique

**v1 → v2 (2026-10-16).** La version v1, rédigée par le tech lead, portait deux
défauts relevés par la session mobile avant toute écriture de code :
(1) elle activait la clé à `/enrolment/complete`, ce qui rendait l'invariant D4
contournable ; (2) elle ne prévoyait aucune route permettant au PDP de vérifier le
code de récupération. Les deux corrections sont intégrées ci-dessus et l'ADR est
verrouillé dans cette forme.

## Amendement 2026-10-17 — réenrôlement (flux D)

L'ADR v2 ne couvrait que le premier enrôlement. Trou relevé par la session
mobile avant toute écriture de code. Décision :

**Le réenrôlement passe par la MÊME route `POST /device/register`**, qui
accepte en plus l'ancien code de récupération. Aucune route de vérification
de code n'est créée.

**Invariant de réenrôlement (R1) :** si le compte possède déjà une clé
ACTIVE, `/device/register` EXIGE et VÉRIFIE l'ancien code de récupération.
Sans lui, la route refuse. Sans cet invariant, un tiers enregistrerait une
clé sur un compte existant — l'attaque même que le système combat.

**Motif du refus d'une route de vérification séparée.** Une route « vérifie
ce code » serait un oracle à deviner, interrogeable sans autre coût qu'un
appel HTTP, et séparerait la vérification de l'action qu'elle autorise
(fenêtre de course, ou jeton à gérer). Lié à `/device/register`, chaque
tentative exige une chaîne d'attestation valide et un défi signé : le coût
d'un essai devient matériel, pas réseau.

**Réponse uniforme.** Code erroné, attestation invalide et défi invalide
renvoient le MÊME statut et le MÊME corps. L'appelant n'apprend jamais
lequel a échoué.

**Essais et délai (ES-21).** Le compteur est AUTORITAIRE côté PDP, là où le
code est vérifié (REENROL_ATTEMPTS, LOCK_BASE, LOCK_MAX). Le délai affiché
par l'application n'est qu'un reflet de la réponse du serveur : un délai
purement local ne protège de rien, un attaquant utilisant son propre client.
Conforme à B1a-2 (serveur autoritaire, délai local). Le compte n'est JAMAIS
bloqué (décision du 2026-09-25) : seul cet appareil attend, l'USSD reste
disponible (écran E-21).

**Après un réenrôlement réussi :** l'ancienne clé est RÉVOQUÉE, la nouvelle
est EN ATTENTE, un NOUVEAU code est émis, et l'invariant D4 s'applique de
nouveau — la nouvelle clé ne devient ACTIVE qu'après confirmation du nouveau
code. L'ancien code ne vaut plus rien.
