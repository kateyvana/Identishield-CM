# ADR-030 — Limitation par délai croissant sur l'appareil demandeur, jamais par verrouillage de compte

**Statut :** FERME
**Date :** 2026-09-07
**Source :** ISC-AMD-01 ; OWASP Authentication Cheat Sheet ; OWASP API Security Top 10 (API2:2023)

## Contexte
Le code de récupération est un point de récupération d'identifiant : OWASP impose de le traiter comme un point d'authentification en matière de force brute. Une première proposition — blocage du compte pendant 24 heures après deux échecs — a été rejetée en revue : un attaquant qui tape deux codes erronés rendrait le compte indisponible à son titulaire légitime. C'est un déni de service par verrouillage (CWE-645), défaut du même type que celui remonté en production par le candidat dans son activité QA.

## Décision
Après REENROL_ATTEMPTS échecs, un délai croissant s'applique à l'appareil demandeur (identifiant d'installation) et à l'origine réseau, à partir de LOCK_BASE, doublant à chaque échec, plafonné par LOCK_MAX (valeur de départ : 24 h). Le compte visé n'est jamais restreint : le titulaire continue d'utiliser son appareil actif sans en être informé autrement que par une notification informative (EF-47). Les échecs sont comptés par compte pour déclencher une alerte console au-delà d'ALERT_REENROL (ES-24), sans aucune restriction. Toutes les réponses sont uniformes en contenu, code et temps (ES-22).

## Alternatives rejetées
- **Verrouillage du compte après N échecs, durée fixe** — transforme la protection en arme de déni de service.
- **Limitation par appareil seul** — contournée par réinstallation de l'application ; d'où le cumul avec l'origine réseau.
- **Limitation par origine réseau seule** — pénalise tout un quartier derrière une même sortie internet.

## Conséquences
- ES-21, ES-22, ES-24 ; cas d'abus AC-14, AC-15, AC-16.
- Nouveau composant EnrolmentThrottle ; table enrolment_attempt.
- Paramètres REENROL_ATTEMPTS, LOCK_BASE, LOCK_MAX, ALERT_REENROL.
- Ce qui compte n'est pas ce qui bloque : le comptage par compte alimente l'alerte, jamais une restriction.

## Références
OWASP Authentication Cheat Sheet — « care must be taken to prevent [lockout] from being used to cause a denial of service by locking out other users' accounts » ; délai croissant recommandé plutôt que durée fixe. OWASP API2:2023 — les points de récupération sont des points d'authentification. CWE-645.

## Amendement 2026-09-25

**Source :** ES-27 et EF-47 (ISC-SRS-FR v1.4) ; décisions D-5 et D-7 d'ISC-AMD-02 v1.1 ; levée du propriétaire du 25/09/2026. Le texte d'origine ci-dessus est conservé.

- **Qui est prévenu, et comment.** ~~Le titulaire continue d'utiliser son appareil actif sans en être informé autrement que par une notification informative (EF-47).~~ ES-27 et EF-47 visent deux moments différents :
  - **avant un ré-enrôlement réussi** (tentatives en cours), l'appareil **actuellement lié** reçoit l'alerte, avec une réponse signée « c'est moi / ce n'est pas moi » (ES-27). « Ce n'est pas moi » passe le compte en FROZEN et gèle les ré-enrôlements pendant REENROL_FREEZE ;
  - **après un ré-enrôlement réussi**, l'appareil **révoqué** ne reçoit qu'une notification informative, sans aucune action (EF-47, ADR-010).
- **Toujours aucune restriction du compte du fait d'un tiers.** Le délai croissant porte sur l'appareil demandeur et l'origine réseau, jamais sur le compte (ES-21). Le gel du ré-enrôlement n'est déclenché que par le titulaire lui-même, par une réponse signée de l'appareil lié.
- **LOCK_MAX** est réglable par le propriétaire (par exemple 24 h) ; sa valeur vit dans `config/ruleset.yaml`.
- Le comptage par compte continue d'alimenter l'alerte console au-delà d'ALERT_REENROL (ES-24).

## Amendement du 2026-10-25 — application du gel des ré-enrôlements à `/device/register` (L-B5-2)

**Statut : PROPOSÉ** (décision du superviseur technique du 2026-10-25, rédigée par le couloir A ;
signée par la propriétaire).

**Constat.** « Ce n'est pas moi » pose `reenrolFrozenUntil = now + REENROL_FREEZE` (machine A1,
`POST /trust/{accountId}/not-me`, ADR-041 amendement du 2026-10-25), mais `/device/register` ne le
consultait pas : un ré-enrôlement restait possible pendant le gel (constaté le 2026-10-24).

**Décision : réponse UNIFORME, aucun code distinct.** ES-22 est le document le plus sûr et il
gagne. Pendant `reenrolFrozenUntil`, `POST /device/register` (donc `/enrolment/complete` côté
cœur) rend **exactement** la réponse de l'échec de code — `401 RECOVERY_INVALID`, même contenu,
même code, même durée : toutes les vérifications sont exécutées (le PBKDF2 du code compris), le gel
est lu en lecture seule (`TrustStateMachine.peek`) pour **chaque** compte déjà lié, gelé ou non. Le
PDP **écrit une entrée d'audit** (`event REENROL_REFUSED`, `cause REENROL_FROZEN`, `accountId`,
`reenrolFrozenUntil`, `occurredAt` ; aucun secret) et **compte la tentative** (ES-24 : par origine,
installation et compte ; le compte n'est jamais bloqué, ES-21). Après l'échéance, le même appel
réussit. Alternative écartée : `403 REENROL_FROZEN` distinct — plus lisible pour le titulaire, mais
il dirait à un tiers que son attaque a été remarquée et que le compte est défendu.

**Conséquences.** `DeviceEnrolment` dépend de `TrustStateMachine` (lecture) et d'`AuditLog`
(écriture par le seul composant autorisé) ; tests `DeviceEnrolmentFreezeTest` (refus pendant le
gel byte-identique à un code faux, vérifications toutes exécutées, comptage, audit ; acceptation
après l'échéance à l'horloge virtuelle ; compte jamais vu non gelé) ; une mutation (gel ignoré →
le test rougit). Le couloir B ferme L-B5-2. Mesure de la fenêtre de temps sur le vrai service :
non faite ici (unitaire) — à faire comme pour AC-16 lors de l'étape téléphone.
