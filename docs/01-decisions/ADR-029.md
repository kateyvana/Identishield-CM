# ADR-029 — Code de récupération à affichage unique comme facteur de ré-enrôlement

**Statut :** FERME
**Date :** 2026-09-07
**Source :** ISC-AMD-01 ; revue de conception des 30–31 août 2026 ; vérification empirique du 31/08/2026

## Contexte
La logique de ré-enrôlement de la v1.1 reposait sur trois voies de rétablissement de la confiance : confirmation par l'ancien appareil, confirmation par un contact de confiance, expiration automatique de la probation. Trois constats les ont invalidées : un ancien appareil volé est aux mains de l'attaquant, donc lui laisser un pouvoir d'approbation est une faille ; l'expiration automatique récompense l'attaquant patient (T-05) ; la désignation d'un contact de confiance est optionnelle et rarement effectuée. Par ailleurs, l'application déployée sur le marché a été vérifiée le 31/08/2026 : trois appareils actifs simultanément sur un compte, aucune notification, fonctionnement sans SIM — aucune liaison exclusive vérifiée par le serveur.

## Décision
Lors de tout enrôlement réussi, le PDP génère un code de récupération, le transmet une seule fois à l'application, et n'en conserve qu'une empreinte cryptographique à sel unique. Tout ré-enrôlement exige ce code, puis le PIN. Aucun mot de passe à usage unique n'est émis ni accepté sur ce parcours. Le code est consommé à l'usage et régénéré. L'application affiche le code sur une vue protégée contre la capture d'écran (ES-23).

L'aiguillage entre premier enrôlement et ré-enrôlement repose sur un seul critère : la présence d'une clé publique enregistrée pour le compte (ES-17b). Aucun signal réseau, aucun motif déclaré n'y entre.

## Alternatives rejetées
- **Confirmation par l'ancien appareil** — donne au voleur d'un téléphone le pouvoir d'approuver un enrôlement.
- **Expiration automatique vers la confiance** — récompense l'attaquant patient ; contredit le profil T-05 du modèle de menace.
- **Contact de confiance obligatoire** — suppose une désignation préalable que la majorité des utilisateurs n'effectue pas ; reporté au traitement du canal USSD (QO-19).
- **Refus du premier enrôlement après changement de SIM** (ADR-013) — le serveur ne peut distinguer une reconduction légitime d'une frauduleuse ; le refus pénalise la victime.

## Conséquences
- ADR-010 et ADR-013 renversés ; ADR-015 réduit. OB-7 retirée.
- ES-03, ES-03b, ES-13, ES-14, ES-17, EF-28 retirées ; ES-03c, ES-13b, ES-14b, ES-17b, ES-18 à ES-24, EF-45 à EF-47 ajoutées.
- L'OTP n'est sollicité qu'une fois dans la vie du compte, au premier enrôlement.
- Nouveau composant RecoveryCodeStore ; table recovery_code ; paramètre CODE_LENGTH.
- Le risque résiduel se déplace vers la perte du code par l'utilisateur ; la voie de résolution — vérification physique au comptoir — reste à formaliser (ISC-AMD-01 §8, point 1).
- Le hameçonnage du code de récupération n'est pas traité : même famille que le hameçonnage du PIN, hors périmètre déclaré.

## Références
Modèle des clés à affichage unique : AWS IAM access keys ; codes de secours TOTP (Google, GitHub). NIST SP 800-63B §6.1.2.

## Amendement 2026-09-25

**Source :** décision du propriétaire du 25/09/2026 (D-1 d'ISC-AMD-02 v1.1) ; ES-19 v1.4 (ISC-SRS-FR v1.4) ; levée du propriétaire du 25/09/2026. Le texte d'origine ci-dessus est conservé.

- **Ordre des facteurs au ré-enrôlement.** ~~Tout ré-enrôlement exige ce code, puis le PIN.~~ Tout ré-enrôlement exige **le PIN, puis le code de récupération**. C'est le même déroulé que le service opérateur : le numéro, puis le PIN, puis le serveur décide. Un compte inexistant et un PIN faux reçoivent une réponse uniforme (ES-22). L'échec de l'un des deux facteurs interrompt le parcours sans révéler lequel a échoué (ES-19).
- **Inchangé :** code à affichage unique, haché salé seul conservé, consommé à l'usage et régénéré, aucun OTP sur ce parcours, vue protégée contre la capture (ES-18, ES-23).
- **Précision (ES-25, v1.4) :** la nouvelle clé n'est enregistrée qu'après validation du code de récupération.
